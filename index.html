Drydock

// NOTHING SAILS UNTIL IT LEAVES THE DOCK

Plan-first parallel execution for Claude Code. A rigorous plan document is the source of truth; subagents execute it in parallel waves with disjoint file ownership; a conformance audit gates every wave; and what execution learned flows back into your docs.

DRAFT 2M — THE PROBLEM

Parallel agents fail two ways

They collide — two subagents editing the same file — or they drift: green tests, clean review, and a diff that quietly does things nobody asked for. Quality review can't catch drift, because drifted code is often good code. It's just not the code the plan specified.

Drydock treats the plan as a contract: every task declares the files it owns, the criteria that define done, and the things it must not do. Then an auditor checks the actual diff against all three — and never takes an executor's word for anything.

DRAFT 4M — EVIDENCE, HONESTLY LABELED

No benchmarks yet. On purpose.

Plugins in this genre love numbers. We'll publish ours when we have field data worth your trust. What we have today is an adversarial self-audit: before shipping the auditor, we red-teamed it — a dry-run with a compliant executor and a rogue one that edited a file it didn't own, then omitted it from its report.

▣ Verified (adversarial dry-run, 2026-08-18)

  • Full lifecycle executes: baseline → plan → parallel waves → audit → block → remediate → pass → deviations logged
  • The auditor caught an ownership breach and a dishonest completion report while every test passed green
  • The dry-run exposed a defect in our own design — combined diffs can't attribute changes per task — fixed in v0.3.0 with mandatory per-task checkpoint commits

▢ Not yet verified (requires live field use)

  • Per-task model right-sizing precedence in your Claude Code version
  • Worktree isolation on a real multi-wave plan
  • Gate compliance rate across real executions — being measured during the internal pilot

Full method and findings: the self-audit report. A verification tool that hid its own unknowns wouldn't deserve the name.

Green tests. Blocked wave.

From the dry-run. Two parallel tasks; T1.1.2 finished its own work, then "helpfully" touched a file owned by its sibling — and left it out of the report.

Every acceptance criterion passed. A quality review would have shipped it. The conformance audit blocked it — that gap is the whole product.

DRAFT 8M — HOW IT WORKS

One contract, five consumers

Everything reads and writes a single versioned plan format. The plan isn't documentation of the work — it is the work order.

  • planwrightWrites the plan. Practices interview, real codebase exploration, batched clarifications into a Decision Log, phases → parallel waves → atomic tasks with disjoint file ownership, per-task model tiers, an adversarial pressure-test before you ever see it. Zero implementation code.
  • youApprove. Status flips to APPROVED by a human, only ever by a human. This is the waterline.
  • executorsBuild, one task each. Fresh context, only their task block. May write only owned files; must verify their own criteria; must report deviations; must checkpoint-commit. Optional git-worktree isolation per plan.
  • wavecheckAudits every wave. Ownership per commit, forbidden list, criteria re-executed, reports cross-checked against the real diff. PASS opens the next wave; BLOCK freezes the plan. Contract breaches get no retries.
  • replanPatches, never regenerates. Human-invoked only. Re-verifies assumptions, replaces only invalidated tasks, preserves the Decision Log and completed-wave history.
  • reconcileCloses the loop. Deviations and failed assumptions become proposed diffs to CLAUDE.md, ADRs, and architecture docs — proposed, never auto-applied — so the next plan starts from reality.

DRAFT 12M — QUESTIONS

Asked and answered

Isn't this heavy for small tasks?
Yes. For a one-file fix, the process costs more than the work — don't use it. Drydock earns its keep on multi-file changes, parallel execution, and teams. A single-phase, single-wave plan is legitimate; inflating structure to look thorough is an anti-pattern the planner itself refuses.
How is this different from other planning plugins?
Most plan, then hope. Drydock's differences: waves are genuinely parallel with ownership enforced against real diffs; the auditor never trusts executor reports; replanning is a surgical patch with immutable history; and reconcile feeds execution learnings back into your docs — the loop nobody else closes.
Does it review code quality?
No — deliberately. Wavecheck audits conformance; a separate fresh-context quality review task runs after it passes. Pairs well with your existing review tooling, and with ponytail, which owns minimalism.
Can the model skip the gates?
The gates are named as blocking instructions inside every plan the planner writes — and we're measuring compliance during the pilot instead of asserting it. The one gate that's mechanically absolute: a human flips APPROVED, and replan cannot be invoked by the model at all.
Why "Drydock"?
Where ships get built, inspected, and repaired — out of the water. Nothing sails until it leaves the dock.
